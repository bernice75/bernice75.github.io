1. Cyder Kiosk: C# 레거시 키오스크 Electron 전환 개발

  • 기간: 2026.04 ~ 현재
  • 소속: (주)한국밴서비스
  • 기술: Electron, React, TypeScript, MySQL, SerialPort, electron-builder
  • 역할: 레거시 분석, Shell(메인 프로세스)/UI 분리 및 책임별 모듈 구조 설계, electron-updater 기반 Semantic Versioning 업데이트 정책 설계, AI 도구를 활용한 구현 생산성 향상 및 결과물 검증

목적 도출

2021년에 완성된 C# 기반 키오스크 프로그램은 수정 반영 방식과 배포 절차에 대한 문서가 남아 있지 않았습니다. 기존에는 파일 서버에 실행 파일을 올려두면 담당자가 이를 내려받아 매장에서 직접 재설치하는 방식으로 배포가 이뤄졌고, 별도의 자동 업데이트 체계는 없었습니다. 결함이 발견되어도 어떤 방식으로 수정하고 배포해야 하는지 파악하기 어려웠고, 결제·현금 모듈·프린터 등 하드웨어 연동 흐름도 기존 코드에 의존해야 했습니다.

무엇을 했는가

  • C# 키오스크의 결제, 현금 모듈, 프린터, 상품 조회, 매장 인증 흐름 분석
  • Shell(메인 프로세스)과 UI(렌더러)를 분리하고, Shell 내부를 DB 연결·쿼리, 외부 API 호출, 현금 모듈 제어, 결제 모듈 제어, 프린터 제어 5개 모듈로 책임별 분리
  • VAN 결제, Serial 현금 모듈, ESC/POS 영수증 출력 로직의 TypeScript 기반 하드웨어 연동 모듈 경계 정의
  • 바코드 상품 조회, 장바구니, 카드·현금·QR·NFC 결제, 현금영수증, 영수증 출력, 거래 내역, 관리자 설정 구현 결과 검증
  • 외부 설정 파일, 환경 변수, 로컬 인증 저장소를 활용한 민감 정보 분리
  • 관리자 비밀번호 해시 저장, 초기 매장 인증·재인증·비밀번호 변경 흐름 분리
  • 개발용 mock 환경과 운영용 실제 장비 환경 분리
  • Electron Builder 기반 Windows x64/ia32 설치 파일 패키징 및 릴리즈 구조 구성
  • electron-updater 기반 Semantic Versioning(major/minor/patch) 업데이트 정책 도입: 메이저·마이너 버전은 필요 시 수동 업데이트, 패치 버전은 결제 진행 중이 아닌 경우 자동 업데이트

어떻게 해결했는가

  • 신규 키오스크는 매장별 UI 변경과 결제 옵션 확장이 반복될 가능성이 높았기 때문에, 팀 내 유지보수 가능성과 동적 UI 변경의 대응력을 우선해 React 기반 구조를 선택. 사내에서 Electron 기반 영수증 출력 프로그램을 이미 운영 중이었고 Windows 설치 파일 패키징 경험도 있었기 때문에, 운영 경험과 배포 방식의 일관성을 고려해 Electron + React 조합을 채택
  • VAN 결제·Serial 현금 모듈·ESC/POS 프린터 연동 로직을 처음부터 독립 모듈로 분리. 결제 실패, 현금 모듈 응답 지연, 프린터 출력 오류가 서로 전파되지 않도록 장애 범위를 격리하고, 개발 환경에서는 mock 모듈로 테스트할 수 있게 구성. 운영 장비나 통신 방식이 바뀌더라도 해당 모듈만 교체할 수 있는 구조를 우선함.
  • 사내에 남아 있던 기존 C# 프로젝트를 직접 확인해 결제·현금 모듈·프린터 연동 흐름과 운영 설정 방식을 분석. 이 과정에서 민감 정보가 애플리케이션 내부에 포함될 수 있는 구조적 위험을 확인했고, 신규 구조에서는 하드웨어 설정, DB 접속 정보, 인증 정보를 외부 설정 파일과 환경 변수로 분리해 배포 바이너리에 포함되지 않도록 설계함.
  • 업데이트 정책은 Semantic Versioning 기준으로 구분. 메이저·마이너 버전은 UI 변경이나 편의 기능 추가처럼 선택적 요소가 대부분이라 현장 확인이 필요할 때만 수동으로 적용하도록 하고, 패치 버전은 동작 결함이나 보안 문제를 보완하는 성격이라 결제가 진행 중인 경우를 제외하고는 반드시 자동으로 적용되도록 구성.

성과

  • 문서가 남아 있지 않은 레거시 키오스크를 분석해 수정 가능한 구조로 전환
  • 하드웨어 연동 로직을 모듈화해 결제·현금·출력 흐름의 유지보수성 개선
  • 민감 정보가 앱 코드나 배포 바이너리에 직접 포함되지 않도록 운영 보안 기준 정립
  • 파일 서버 업로드 후 담당자가 수동으로 재설치하던 배포 방식을 electron-updater 기반 자동/수동 업데이트로 전환해 배포 시 현장 개입 필요성 감소

2. DeployX: SSH 기반 배포 운영 통제 플랫폼

  • 기간: 2026.03 ~ 2026.06
  • 소속: (주)한국밴서비스
  • 유형: 사내 업무 프로젝트
  • 기술: Node.js, React, SSH/SFTP, WebSocket Log Streaming, MySQL/PostgreSQL, Apache Reverse Proxy, Blue-Green Deployment, RBAC, Audit Log, SMTP Notification, systemd/PM2
  • 역할: 수동 배포 프로세스 분석, PRD/Plan 기반 요구사항 정의, 배포 단계별 진행 상황·결과 기록 플로우 설계, Blue-Green 전환 구조 설계, 권한/승인 정책 설계, AI 도구를 활용한 구현 생산성 향상 및 결과물 검증, 운영 배포 환경 구성, 장애 대응 흐름 문서화

목적 도출

입사 초기 Jenkins와 Bitbucket을 활용해 CI/CD를 구축했던 흔적을 발견했습니다. 기존 환경을 최대한 재사용하기 위해 Jenkins 서버, CI/CD 스크립트, 배포 설정 위치를 추적했지만 인증 토큰 외에는 실질적인 운영 흔적이 남아 있지 않았습니다.

새로운 CI/CD 파이프라인을 바로 구축하려면 서버 위치, 접근 권한, 빌드·배포 스크립트, 롤백 정책, 운영 책임 범위를 다시 정의해야 했습니다. 당시 실제 병목은 빌드 자동화 자체보다 SSH 서버에 직접 접속해 SFTP로 파일을 업로드하고, 서버에서 수동 실행·확인하는 배포 절차의 누락 가능성과 추적 불가 문제였습니다.

따라서 프로덕션 인프라를 즉시 교체하기보다, 기존 수동 배포 절차를 먼저 단계별로 진행 상황과 결과를 기록할 수 있는 형태로 표준화하고, 배포 이력·로그·실패 원인·롤백 기준을 추적 가능한 형태로 전환하는 내부 운영 보조 시스템을 설계하는 것을 목표로 삼았습니다.

초기 버전은 SSH/SFTP 기반 JAR 업로드, 원격 실행, 로그 스트리밍, 배포 진행 상황 기록에 초점을 두었습니다.
이후 실제 운영 적용을 고려하면서 단순 배포 실행 도구가 아니라, 권한·승인·감사·롤백·Blue-Green 전환·알림까지 포함하는 배포 운영 통제 플랫폼으로 목표를 확장했습니다.

특히 일부 운영 서버가 CentOS 기반 Apache Reverse Proxy 구조를 사용하고 있었기 때문에, 애플리케이션이 서버별 설정을 직접 보유하지 않고 DB에 저장된 서버·서비스 설정을 기준으로 Apache proxy template, active symlink, blue/green port, health check URL을 관리하도록 구조를 정리했습니다.

무엇을 했는가

  • SSH/SFTP 기반 JAR 업로드 및 원격 배포 실행 흐름 구현
  • WebSocket 기반 실시간 배포 로그 및 애플리케이션 로그 스트리밍 구현
  • 배포 상태를 UPLOADING, DEPLOYING, SUCCESS, FAILED, ROLLBACK_SUCCESS, ROLLBACK_FAILED 값으로 정의하고, 단계별 진행 상황과 결과를 순차적으로 기록하는 플로우 구성
  • 배포 실패 단계와 실패 원인을 failed_step, failure cause로 표준화하고, UI 상태·DB 이력·다운로드 로그가 동일한 실패 원인을 공유하도록 보정
  • 최근 성공 버전 기준 수동 롤백 기능 구현
  • CentOS Apache Reverse Proxy 기반 Blue-Green 배포 구조 설계 및 구현
  • Apache proxy template 치환, active conf symlink 전환, Apache reload, public health check, 실패 시 proxy 복구 흐름 구현
  • Blue-Green 전환 성공 후 이전 active port 정리 스크립트 지원
  • ADMIN / OPERATOR / VIEWER 기반 RBAC 적용
  • 일반 OPERATOR 배포 요청은 승인 흐름으로 전환하고, 긴급 배포 권한이 있는 OPERATOR만 즉시 배포 가능하도록 정책 구현
  • 관리자 UI에서 사용자 생성, 로그인 허용/차단, 권한 관리 기능 구현
  • 배포 실행자, 승인자, 요청자 정보를 audit log와 deployment log에 기록
  • CI 토큰 기반 산출물 업로드 API 구현
  • CI 토큰은 애플리케이션 단위로 발급하고, 업로드 성공 시 즉시 만료되는 1회성 토큰 정책 적용
  • SMTP 기반 배포 결과 알림 구조 구현
  • 배포 성공/실패 시 실행 로그 및 실패 원인을 txt 첨부파일로 발송하도록 설계
  • 개발 PostgreSQL, 운영 MySQL 5.6 환경을 모두 지원하도록 DB driver를 분리하고, DB adapter·placeholder 변환·pagination count 쿼리를 운영 호환성 기준으로 보강
  • 운영 배포를 위해 프론트 정적 파일, 백엔드 systemd + pm2-runtime, Apache reverse proxy 구성을 정리

어떻게 해결했는가

  • Jenkins/GitHub Actions를 즉시 도입하기보다, 현재 조직의 실제 배포 병목인 “수동 SSH 배포의 추적 불가” 문제를 먼저 해결
  • 애플리케이션 코드가 서버·서비스 정보를 하드코딩하지 않고, DB에 저장된 설정을 기준으로 배포 흐름을 결정하도록 설계
  • Apache Reverse Proxy 환경에서는 애플리케이션 포트 전환과 proxy symlink 전환을 분리해 Blue-Green 구조를 구성
  • 레거시 서버마다 Apache 제어 권한이 달라 sudo -n을 일괄 적용하지 않고, apache_sudo_mode를 호스팅 서버 단위 설정으로 분리. 기본값은 기존 서버 동작을 깨지 않는 NONE으로 두고, NOPASSWD 서버에만 sudo 실행 전략을 적용
  • 운영 보안을 위해 개발 환경은 localStorage/Bearer token, 운영 환경은 HttpOnly Secure SameSite cookie 기반 세션 전략으로 분리
  • 개발 DB는 PostgreSQL, 운영 DB는 MySQL 5.6이었기 때문에 특정 버전 이상에서 가능한 window function 기반 pagination count를 사용할 수 없었음. 운영 호환성을 우선해 목록 조회와 count 조회를 분리하고, MySQL 5.6에서도 동작하는 쿼리 구조로 설계
  • CI 토큰은 배포 권한이 아닌 산출물 업로드 권한으로 제한하고, 7일 만료 및 업로드 성공 즉시 폐기 정책 적용
  • DeployX가 빌드 시스템까지 대체하지 않도록 경계를 정하고, 외부 CI 산출물을 안전하게 수신·등록·배포하는 CD 도구로 설계

성과

  • SSH 접속 후 수동으로 수행하던 배포 절차를 웹 기반 반자동 배포 흐름으로 표준화
  • 배포 중 발생하는 로그, 실패 단계, 실패 원인을 화면과 DB 이력으로 추적 가능하게 개선
  • 단순 성공/실패 기록을 넘어, 운영자가 실패 단계와 원인을 사후 분석할 수 있는 배포 추적 체계 마련
  • 운영 서버의 Apache Reverse Proxy 구조를 고려해 Blue-Green 배포와 proxy 전환 흐름을 도입
  • 배포 실패 시 신규 포트 프로세스 정리, proxy 복구, 실패 원인 기록 등 후속 조치 흐름을 보완
  • 배포/롤백 권한을 사용자 역할과 승인 정책에 따라 통제하도록 개선
  • 배포 요청자·승인자·실행자·대상 버전을 이력화해 배포 전후의 책임 경계와 판단 근거를 시스템에 남김
  • 회원가입 없이 관리자 기반 계정 생성 및 로그인 허용 정책으로 운영 보안 기준 강화
  • CI/CD 전체 도입 이전에도 IntelliJ bootJar 산출물을 안전하게 등록·추적할 수 있는 중간 자동화 구조 마련

3. Food Kiosk 시스템 개발

  • 기간: 2025.08 ~ 2025.10
  • 유형: 별도 계약 프로젝트
  • 기술: React, Nginx, WebSocket, C#, TCP/Serial 통신 연동, POS/Kiosk
  • 역할: 키오스크 데이터 객체 설계, 외부 장치 연동 구조 설계, 통신 프로토콜 협의, 운영 환경 설정 분리

목적 도출

매장 운영 효율 개선을 위해 신규 키오스크 시스템 도입이 필요했습니다. 기존 POS 시스템과 데이터 구조가 맞지 않을 경우 주문·결제·상품 데이터의 이중화와 정합성 문제가 발생할 수 있었고, 프린터·결제 단말기 등 주변 장치와의 연동 안정성도 확보해야 했습니다.

무엇을 했는가

  • 기존 POS 시스템의 데이터 스키마를 분석해 키오스크 내부 데이터 객체 설계
  • 주변 장치 제어를 담당하는 C# 프로그램과 WebSocket 기반으로 연동하는 구조 설계
  • TCP/Serial 통신을 담당하는 외부 프로그램과의 데이터 구조 및 문자열 프로토콜 협의

  • 외부 서버 URL, 호스트, 포트 등 운영 환경 정보를 환경 변수와 설정값으로 분리

어떻게 해결했는가

  • 키오스크(React)와 장치 제어 프로그램(C#) 간 통신 방식으로 WebSocket을 선택. REST polling은 장치 처리 완료 시점을 즉시 알기 어렵고, 단순 HTTP callback은 키오스크 측에 별도 로컬 수신 엔드포인트와 생명주기 관리가 필요해 제외. 주방빌 출력 흐름(키오스크 요청 → C# 영수증 가공 → 외부 TCP 서버 전달 → 응답 수신 → 키오스크에 결과 전달)처럼 요청부터 외부 TCP 응답까지 하나의 상태 흐름으로 추적해야 했고, C# 장치 제어 프로그램이 결과를 비동기로 되돌려줘야 했기 때문에 WebSocket을 선택
  • 기존 POS 스키마는 키오스크에 불필요하게 복잡한 구조였고, 메뉴와 옵션이 동일 테이블에 혼재되어 있으면서 구분 가능한 인자가 없는 상태. POS 스키마를 그대로 사용하는 대신 키오스크 전용 스키마를 별도 설계하고, 메뉴를 직접 검색해 매핑하는 방식으로 협의해 데이터 정합성 문제를 우회

성과

  • 기존 POS와 신규 키오스크 간 데이터 정합성 확보
  • 프린터·결제 단말기 등 이기종 장치 연동 경험 축적

  • Google Play의 target API level 요구사항을 충족하지 않으면 앱 업데이트 제출이 제한되고, 이후 최신 Android 버전 기기 사용자에게 앱 노출과 신규 설치가 제한될 수 있는 상황. 전체 구조 개편보다 스토어 배포 지속성과 기존 기능 회귀 최소화를 우선해 API 34 대응 범위를 필수 변경으로 제한했고, Android 14 대상 앱에서 요구되는 registerReceiver export flag 지정 등 정책 대응에 필요한 수정만 선별해 빠른 재배포 가능성을 확보
  • 장기적으로는 추출 APK 기반 운영을 지속하지 않고, Flutter 기반으로 더 고도화된 앱을 새로 개발해 기존 앱을 대체하는 방향을 선택. 이를 통해 소스 기반 빌드, 서명 키 관리, 기능 개선이 가능한 유지보수 체계로 전환

성과

  • 기존 사용자 대상 서비스 접근 경로를 우선 복구해 운영 공백 완화

목적 도출

매장별 상품 데이터가 파편화되어 동일 상품도 서로 다른 명칭으로 관리되고 있었습니다. 이로 인해 정확한 매출 집계와 통계 산출이 어려웠고, 관리자·매니저·가맹점주 등 권한별 데이터 접근 범위를 명확히 나눌 필요가 있었습니다. 매출 ASP 사이트를 개설하는 과정에서, 기존 매출 확인 앱을 Flutter 기반으로 고도화해 웹과 모바일에서 동일한 매출 데이터를 조회할 수 있도록 병행 개발했습니다.

무엇을 했는가

  • 바코드 기반 상품 식별 체계 도입

  • 앱에서 매장별 매출·상품 데이터를 권한 범위에 따라 조회하고, 중앙 시스템과 동기화하는 흐름 구현

어떻게 해결했는가

  • 로그인 사용자 정보를 기존 사내 ERP 테이블에서 조회하는 구조로 연결하면서, 해당 테이블에는 매니저와 가맹점주를 구분하는 권한 컬럼이 없는 상태였음. 별도로 “그룹장” 테이블을 설계해 특정 매장을 매니저로 지정하고, 그 하위에 등록할 가맹점을 별도 스키마로 관리하는 방식으로 권한 계층을 외부에서 구성
  • 권한별 데이터 접근 제어를 DAO 레이어에서 처리한 것은 동일 테이블에 모든 사용자가 혼재하는 구조적 제약에 따른 선택. MyBatis는 해당 프로젝트의 기존 ORM 기준이었고, 매출 조회 쿼리 복잡도가 동적 필터링으로 충분히 처리 가능한 수준이었기 때문에 별도 ORM 전환 없이 유지
  • Flutter 앱은 중앙 ASP 시스템의 권한 모델과 동일한 데이터 접근 범위를 따르도록 설계. SQLite는 앱 내 조회 상태와 일부 현장 조작 데이터를 안정적으로 보관하기 위한 로컬 저장소로 사용하고, 최종 기준 데이터는 중앙 ASP 시스템과 동기화되도록 구성

성과

  • 파편화된 상품 데이터를 표준화해 매출 집계 정확도 개선
  • 권한별 데이터 접근 범위를 시스템화
  • 기존 매출 확인 앱을 Flutter 기반 앱으로 대체해 소스 기반 유지보수와 기능 개선이 가능한 구조 마련

기존 PHP 기반 스마트폰 전용 앱은 전용 PDA와 일반 스마트폰을 모두 지원하기 어려웠고, 현장 작업 흐름에 맞는 기능 확장에도 한계가 있었습니다. CASIO, NewLand 등 전용 스캐너 기기와 일반 스마트폰을 모두 고려한 신규 모바일 솔루션이 필요했습니다.

  • PDA와 일반 스마트폰을 함께 지원하는 확장 가능한 구조 마련
  • 현장 작업 효율 40% 이상 개선
  • 기능 추가 시 초기 분석 시간을 줄일 수 있도록 프로젝트 문서화

7. WebFlux + Netty 기반 동기화 서버 리소스 고갈 장애 분석 및 최적화

  • 기간: 2024.10 ~ 2026.01 (재발 관찰 포함)
  • 소속: (주)한국밴서비스
  • 기술: Java, Spring Boot, Netty, WebFlux, R2DBC, MariaDB
  • 역할: 장애 원인 분석, 메시지 프레이밍 개선, 리액티브 체인 정제, 재발 관찰

목적 도출

POS/키오스크 매출 수신 서버에서 DB 커넥션 풀이 반복적으로 고갈되어 연관 시스템까지 동반 장애가 발생했습니다. 인프라 문서가 전무하고 클라이언트 수정도 기대하기 어려운 상황에서, 애플리케이션 구조와 인프라 장애를 분리해 원인을 추적해야 했습니다.

무엇을 했는가

  • 개행 기준 프레이밍이 대용량 JSON 메시지에 맞지 않아 발생한 예외 분석
  • JsonObjectDecoder 기반 객체 경계 프레이밍으로 교체
  • 중첩 subscribe로 인해 구독 취소와 에러 전파가 끊기던 흐름 분석
  • flatMap 기반 단일 체인으로 리액티브 흐름 평탄화
  • timeout/onErrorResume 기반 예외 처리 표준화
  • 1차 임시 조치 이후 재발한 장애를 재분석하고 구조적 원인 개선

어떻게 해결했는가

  • 장애 추적을 위해 처리 흐름의 단계마다 진행 여부를 확인할 수 있는 로그를 사전에 삽입. 로그가 출력되지 않는 지점으로 처리가 중단된 위치를 특정하고, 발생한 예외 유형으로 원인 범위를 좁히는 방식으로 1차·2차 장애 원인을 구분
  • 코드 리뷰 중 중첩 subscribe 구조를 발견했으나, WebFlux에 대한 사전 지식이 없어 해당 구조가 문제인지 즉시 판단하지 못함. 추적 로그를 먼저 삽입해 실제 장애 흐름을 확인하고, 병행 학습을 통해 중첩 구독이 에러 전파와 커넥션 반환을 끊는 구조적 원인임을 확인한 후 flatMap 기반 단일 체인으로 개선
  • 초기 로깅에 @Slf4j 기반 단순 로그를 사용했으나, 비동기 처리와 Netty 이벤트 루프 전환 과정에서 요청 흐름과 스레드 정보를 함께 추적하기 어렵다는 한계를 확인. HTTP 기반 WebFlux 요청이 아니라 내부 TCP 서버 흐름이 중심이었기 때문에 Micrometer Tracing 자동 계측을 그대로 도입하지 않고, 기존 로깅 구성을 유지하면서 메시지 처리 단위로 수동 Observation을 생성하고 thread id·처리 단계·상관 식별자를 함께 남기는 후속 개선 방향으로 분리

성과

  • 2026.01 이후 동일 원인 애플리케이션 장애 0건으로 마감

10. 그룹웨어 인증·권한 체계 확장

  • 기간: 2025.11 ~ 2026.01
  • 소속: (주)한국밴서비스
  • 기술: Java, Spring Boot, Spring Security, JWT, MariaDB
  • 역할: 인증 연동 구조 설계, 멀티테넌시 권한 모델 설계, ACL 설계

목적 도출

그룹웨어(사내 ERP)와 매출 ASP(가맹점 매출 확인 사이트)는 서로 별도로 운영되는 시스템이지만 "가맹점"이라는 공통 분모로 연결되어 있었습니다. 가맹점주가 매출 ASP를 이용하다 문의를 남기면, 매출 ASP 자체에는 담당자가 가맹점주를 대신해 로그인하고 상태를 확인할 수 있는 권한이 없어 문의 대응이 지연됐습니다. 또한 사내 전용으로 운영되던 그룹웨어를 사용료를 받고 외부 업체에 공개하는 기획이 나오면서, 여러 업체가 하나의 시스템을 함께 쓰는 구조에서 업체 간 데이터 격리가 새로운 과제로 떠올랐습니다.

무엇을 했는가

  • 그룹웨어 담당자의 권한 상태를 기준으로 가맹점 정보 기반 JWT를 발급해 매출 ASP에 로그인 없이 접근할 수 있는 구조 구현
  • 게시물, 직원 일정 등 그룹웨어 내 모든 도메인 데이터를 업체 ID 기준으로 격리하는 멀티테넌시 구조 도입
  • 자사 업체를 마스터로 등록하고 하위 담당자 중 일부에 마스터 권한을 부여해, 마스터 업체 소속과 마스터 권한을 함께 만족할 때만 타 업체 정보를 열람할 수 있도록 구현
  • 담당자가 일반 사용 권한과 마스터 대응 권한을 최대 2개까지 보유할 수 있는 ACL 모델 설계

어떻게 해결했는가

  • 매출 ASP 연동에서는 동일 최상위 도메인 쿠키 공유 방식 대신 만료 시간을 가진 JWT 기반 연동을 채택. 그룹웨어와 매출 ASP는 운영 주체와 데이터 모델이 다른 별개 시스템이었기 때문에, 세션을 공유하기보다 필요한 시점에만 가맹점 정보를 담은 단기 토큰을 발급하는 방식이 결합도를 낮추면서도 CS 대응 흐름을 만족시킬 수 있다고 판단
  • 업체 간 데이터 격리는 도메인 테이블에 업체 ID를 추가하는 방식으로 처리하되, 자사 담당자의 CS 대응 요구를 위해 별도의 "타 업체 조회" 권한 종류를 새로 만들지 않고 기존 권한 모델에 마스터 업체·마스터 권한이라는 조건을 얹는 방식을 선택. 권한 종류를 늘리는 대신 조건을 추가해 담당자가 가질 수 있는 권한 조합을 최대 2개로 제한하고 관리 복잡도를 낮춤

성과

  • 가맹점주 로그인 없이도 담당자가 매출 ASP 화면에 접근해 CS 문의에 즉시 대응할 수 있는 구조 마련
  • 사내 전용 ERP였던 그룹웨어를 다중 업체가 함께 사용할 수 있는 유료 공개형 구조로 확장 가능한 권한 기반 마련
  • 자사 담당자와 외부 업체 담당자의 데이터 접근 범위를 시스템적으로 분리해 정보 노출 위험 최소화

11. 주문 관리 시스템(OMS) 비동기 아키텍처 고도화

  • 기간: 2023.08 ~ 현재
  • 소속: (주)한국밴서비스
  • 기술: Java, Spring Boot, Spring Event, JPA, QueryDSL, MySQL
  • 역할: 주문·배송·입금 업무 전산화, 비동기 아키텍처 설계, 이벤트 추적 구조 설계

목적 도출

초기 구축 단계에서는 수기·엑셀 중심의 주문 접수, 배송, 입금 관리 흐름을 전산화해 운영 리스크와 데이터 오류 가능성을 낮추는 것이 핵심 과제였습니다. 이후 운영 과정에서 외부 택배사 API 응답 지연으로 관리자 화면이 최장 7초간 멈추는 문제가 확인되어, 주문 처리 흐름을 비동기 구조로 고도화했습니다.

무엇을 했는가

  • 엑셀 기반 업무 흐름을 분석해 주문·배송·입금 관리 데이터 모델 설계
  • Spring Data JPA, QueryDSL, MyBatis를 복잡도에 따라 혼합 적용
  • Spring Event 기반으로 주문 저장과 외부 API 호출 책임 분리
  • 트랜잭션 커밋 후 @Async 기반 외부 API 호출 리스너 실행
  • UUID 기반 eventId 발행 및 요청/응답 전문 로깅
  • 실패 건에 대해 현업 담당자가 인지 후 수기 재접수할 수 있는 상태 관리 프로세스 정립

어떻게 해결했는가

  • @EventListener 대신 @TransactionalEventListener(phase = AFTER_COMMIT)와 @Async 조합을 선택. 이번 흐름의 핵심 요건은 외부 택배사 API에 전달할 요청 객체가 DB에 완전히 적재된 상태를 보장하면서도, 사용자가 외부 API 응답을 기다리지 않도록 분리하는 것이었음. 이벤트 publish 자체는 주문 저장 흐름에서 수행하되 외부 API 호출 리스너는 트랜잭션 커밋 이후 비동기로 실행하고, 사용자에게는 200 응답과 함께 처리 준비 상태 코드를 반환하도록 구성. @EventListener는 트랜잭션 컨텍스트 내에서 즉시 실행될 수 있어 DB 커밋 완료를 전제로 하기 어렵지만, @TransactionalEventListener는 원하는 트랜잭션 단계를 기준으로 리스너 실행 시점을 구조화할 수 있어 채택
  • 자동 재시도 방식은 우선 배제하고 수기 재접수 기반 운영 프로세스를 채택. 외부 API는 특정 컬럼값을 기준으로 멱등성을 보장하도록 설계되어 있었으며, 실제 접수 실패의 주된 원인은 서버 일시 오류보다 요청 객체 구성 문제인 경우가 대부분이었음. 이 경우 동일 요청을 자동 재시도해도 성공 가능성이 낮고, 택배 접수 업무는 시간 민감성이 높아 현업 담당자가 실패 사유를 확인한 뒤 수기 접수로 제때 처리하는 것이 더 현실적인 대응이라고 판단. 개발자는 오류 스택과 응답 전문을 분석해 요청 생성 로직을 보정하는 역할로 분리

성과

  • 외부 API 응답을 기다리지 않고 처리 준비 상태를 즉시 응답하도록 분리해 사용자 대기 시간 7초 → 150~200ms 수준으로 단축
  • 수기 업무 전산화를 통해 주문 처리 시간과 휴먼 에러 가능성 감소
  • 월 5,000건 이상 주문 처리 기반 마련

12. 현대백화점 주머니 H.Point 통합 프로젝트

H.Point 멤버십 시스템에 VIP 마일리지 적립이 가능하도록 기능을 추가해야 했습니다. 기존 적립 코드에 영향을 최소화하면서 신규 결제 수단과 적립 로직을 안정적으로 반영해야 했습니다.

무엇을 했는가

  • 신규 결제 수단 판단 조건은 하드코딩하지 않고 코드 마스터 테이블에 등록된 값을 기준으로 처리하도록 담당자와 협의. 이후 결제 수단 추가나 코드 변경 시 애플리케이션 수정 범위를 줄일 수 있도록 데이터 기반 관리 방식으로 정리
  • 분기 추가 후 담당자와 함께 VIP 마일리지 적립 대상/비대상, 기존 결제 수단 적립률 유지, 신규 결제 수단 적립 반영 여부를 시나리오로 작성하고 실제 환경에서 검증. 코드 변경 범위를 최소화한 대신, 주요 케이스를 명시적으로 테스트해 기존 적립 로직 회귀 가능성을 줄임

성과

  • 최소한의 코드 수정으로 신규 결제 수단 추가
  • 적립 계산 오류 가능성 감소

13. 그린자켓 앱 고도화

  • 기간: 2023.02 ~ 2023.03
  • 소속: 솔브스
  • 기술: Java, Spring Security, SQL, RDBMS
  • 역할: 비즈니스 로직 정리, 쿼리 성능 개선, 인증 유지 로직 개선

목적 도출

기존 그린자켓 앱 서비스는 중복 코드와 비효율적인 DB 쿼리 구조로 유지보수성이 낮았습니다. 일부 통합 쿼리는 과도한 UNION과 JOIN으로 5분 이상의 응답 지연이 발생했습니다.

무엇을 했는가

  • 로그인, 회원가입, 마이페이지 등 핵심 기능의 비즈니스 로직 재구성
  • 사용되지 않거나 중복된 코드 제거
  • 통합 쿼리를 비즈니스 단위별로 분리하고 서비스 레이어에서 재조립
  • 조건문 최적화 및 인덱스 추가
  • Spring Security 기반 로그인 유지 로직 개선

어떻게 해결했는가

  • 메인 화면에는 각 서비스별 summary를 함께 표기해야 했는데, 기존 구현은 여러 서비스의 개별 쿼리를 UNION ALL로 묶어 단일 쿼리로 실행하는 방식이었음. 쿼리가 복잡해질수록 실행 계획이 비대해지고 부분 최적화가 어려워졌기 때문에, 각 서비스 단위로 쿼리를 분리하고 메인 화면의 서비스에서 각 서비스별 메서드를 호출해 비즈니스 레이어에서 결과를 통합하는 방식으로 전환. 쿼리를 서비스 책임 단위로 쪼개면서 인덱스 튜닝과 조건 최적화를 독립적으로 적용할 수 있었고, 3~5분 이상 걸리던 조회를 약 350ms 수준으로 개선
  • Spring Security remember-me 기반 로그인 유지 기능이 동작하지 않는 문제를 진단하는 과정에서, remember-me 토큰 생성에 필요한 커스텀 설정이 일부만 적용되어 쿠키/토큰이 정상 발급되지 않는 상태임을 확인. 레거시 설정 코드를 역추적하기보다, 커스텀 설정을 임시 제거하고 Spring Security 기본 remember-me 설정으로 정상 동작 기준선을 먼저 확보한 뒤 필요한 설정만 순차 재적용하는 방식으로 디버깅 범위를 제어

성과

  • 3~5분 이상 지연되던 조회 성능을 약 350ms 수준으로 개선
  • 불필요한 코드와 복잡한 쿼리 구조 정리
  • 로그인 인증 관련 이슈 완화

14. 신용보증재단 모바일 앱 구축 사업

  • 기간: 2022.07 ~ 2023.01
  • 소속: (주)URP
  • 기술: Java, Spring, Oracle, PostgreSQL, EAI, MCI, ECM
  • 역할: 신규 모바일 앱 서버 구축, 레거시 시스템 연동, DB 설계 및 마이그레이션

목적 도출

기존에는 보증 상담과 신청을 처리할 모바일 앱이 없어, 고객 업무가 오프라인 지점 방문과 서류 제출 중심으로 진행되고 있었습니다. 신규 모바일 앱 구축 프로젝트에 투입되어 모바일 업무 흐름을 설계하고, 기존 온프레미스 시스템과의 연동 구조를 정리했습니다.

무엇을 했는가

  • 현업 업무 프로세스 분석 및 플로우 차트 작성
  • 화면 주도 데이터베이스 설계 방식으로 DB 스키마 최적화
  • EAI, MCI, ECM 연계 솔루션과 통합 인터페이스 설계
  • EAI 서버의 SQL 문 ID 인식 문제 트러블슈팅
  • 솔루션별 통신 로직 표준화

어떻게 해결했는가

  • 기존 제공받은 DB 스키마는 웹 시스템 기준으로 설계되어 모바일 업무에 그대로 적용하기에는 불필요하게 비대했고, 기존 웹에서 다루지 않았던 신규 화면이 대부분이었음. 웹 스키마를 단순 이식하는 대신, 모바일 업무 흐름에서 실제로 입력·조회·저장해야 하는 데이터 단위를 기준으로 신규 스키마를 설계. 예약 시스템처럼 기존 구조를 재사용할 수 있는 영역은 유지하고, 신규 모바일 업무에 필요한 화면은 별도 스키마로 분리해 모바일에 맞는 데이터 구조로 정리
  • EAI 솔루션에서 신규 SQL이 인식되지 않는 문제를 진단할 때, DBMS 툴로 쿼리 자체의 오류 여부를 먼저 확인한 뒤 솔루션 반영 절차 문제로 범위를 좁혔음. 폐쇄망 환경의 해당 솔루션은 SQL 파일 배치만으로 신규 SQL이 반영되지 않고, 별도 관리 페이지에서 SQL ID를 수동 등록해야 하는 구조였으나 이 절차가 초기에 공유되지 않았음. 솔루션 문서를 직접 요청해 관리 페이지와 등록 절차를 확인하고 SQL ID를 등록해 해결

성과

  • 상담예약 및 비대면 보증 신청 프로세스 디지털화
  • 마이데이터 연동을 통해 서류 처리 절차의 단축 기반을 마련
  • 신규 API 서버와 기존 레거시 시스템 간 안정적 연동 경험 확보

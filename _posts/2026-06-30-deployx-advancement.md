[이전 글: SSH 배포를 가시화 해보자]({% post_url 2026-03-31-ssh-deploy-visualization %})에서는 SSH 기반 배포 과정을 어떻게 화면에 드러낼지에 대해 정리했습니다.<br>
SFTP로 JAR를 올리고, SSH로 원격 명령을 실행하고, 그 결과를 상태와 로그로 보여주는 것이 첫 번째 목표였습니다.<br>
당시 DeployX는 "배포가 지금 어디까지 진행됐는가"를 사람이 읽을 수 있게 만드는 데 집중한 도구였습니다.

그런데 실제 운영에 가까운 환경에서 계속 사용해보니, 배포 과정을 보이게 만드는 것만으로는 부족했습니다.<br>
운영 도구라면 실패했을 때 원인을 남겨야 하고, 누가 어떤 버전을 배포했는지 추적할 수 있어야 하며, 아무나 바로 운영 배포를 실행할 수 없도록 권한도 통제해야 합니다.<br>
또 레거시 서버마다 다른 권한 모델과 오래된 DB 버전, 서비스별 헬스 체크(health check) 차이도 도구 안에서 흡수해야 했습니다.

이번 글은 DeployX를 단순한 SSH 배포 가시화 도구에서, 실제 운영에 활용할 수 있는 CD 도구에 가깝게 고도화해간 기록입니다.

<br>

## 배포를 "보는 도구"에서 "운영하는 도구"로

처음 만든 DeployX의 핵심은 명확했습니다.

1. JAR 파일을 올린다.
2. 원격 서버에서 기존 프로세스를 종료한다.
3. 새 프로세스를 실행한다.
4. 헬스 체크 결과와 로그를 화면에 보여준다.

이 흐름만 있어도 수동 SSH 배포보다 훨씬 편했습니다.<br>
하지만 운영에 붙이는 순간 질문이 달라졌습니다.

- 실패했다면 어느 단계에서 실패했는가?
- 실패 원인은 UI, DB, 다운로드 로그에 동일하게 남아 있는가?
- 운영 배포 버튼을 누를 수 있는 사람은 누구인가?
- 일반 작업자는 승인 요청만 만들고, 관리자가 승인한 뒤 배포되게 할 수 있는가?
- 배포 이후 누가 어떤 관리 작업을 했는지 감사할 수 있는가?
- 기존 CI에서 만든 산출물을 안전하게 배포 대상으로 넘길 수 있는가?

즉, 배포 자동화와 운영 가능한 배포 시스템은 다른 문제였습니다.<br>
버튼 하나로 배포가 되는 것보다 중요한 것은, 문제가 생겼을 때 사람이 판단할 수 있는 근거와 책임 경계를 시스템에 남기는 일이었습니다.

그래서 이번 고도화의 목표는 Jenkins나 GitHub Actions 같은 범용 CI/CD를 새로 만드는 것이 아니었습니다.<br>
이미 존재하는 레거시 서버 환경과 배포 방식을 존중하면서, 그 위에 통제와 추적, 복구 가능성을 추가하는 것이 목표였습니다.

<br>

## 실패를 설명하고 복구할 수 있어야 했다

첫 번째 전환점은 배포를 실행하는 것에서, 실패해도 기존 서비스를 지키고 원인을 설명할 수 있게 만드는 것이었습니다.<br>
이를 위해 실패 상태를 세분화하고, Blue-Green 전환과 복구 흐름을 만들고, 서버마다 다른 실행 권한을 설정으로 흡수했습니다.

### 실패 상태와 원인을 표준화하기

초기 구현에서도 배포 결과는 성공과 실패로 나뉘었습니다.<br>
하지만 운영에서 필요한 정보는 단순한 `SUCCESS`나 `FAILED`가 아닌 "어느 단계에서 왜 실패했는가"였습니다.

예를 들어 같은 실패라도 의미는 전혀 다를 수 있습니다.

- SSH 연결 전 실패
- JAR 업로드 중 실패
- 새 프로세스 실행 직후 실패
- 내부 헬스 체크 실패
- Apache proxy 전환 실패
- 외부 헬스 체크 실패
- 이전 포트 정리 중 실패

이 상태들이 모두 `FAILED` 하나로만 보이면 운영자는 다시 서버에 접속해서 로그를 뒤져야 합니다.<br>
그래서 배포 상태값과 실패 단계를 더 명확하게 정리했습니다.<br>
특히 Blue-Green 전환 흐름에서는 `PROXY_SWITCH_FAILED`, `SWITCH_APACHE_PROXY`, `TIMEOUT`처럼 실패 지점이 드러나는 값을 남기도록 했습니다.

이 과정에서 확인 경로에 따라 얻을 수 있는 정보가 다르다는 문제가 있었습니다.<br>
`PROXY_SWITCH_FAILED / SWITCH_APACHE_PROXY`로 실패한 배포의 실제 원인은 로그 상단의 요약(summary)에 제공됐고, 이를 직접 확인할 수 있는 사용자는 ADMIN뿐이었습니다.<br>
반면 다운로드 로그에는 전환 시도와 `SWITCH_APACHE_PROXY` 이후의 정리 기록은 남았지만, 요약에 있던 실제 오류 문구가 포함되지 않았습니다.

같은 프록시 전환 실패라도 요약에는 다음처럼 서로 다른 원인이 표시될 수 있었습니다. 아래는 별개의 오류 사례이며, 뒤에서 소개할 한 배포에 두 오류가 함께 발생했다는 뜻은 아닙니다.

```text
Apache proxy switch failed: sudo: sorry, you must have a tty to run sudo
Apache proxy switch failed: bash: /my/bin/path/deployx-switch-apache-proxy: Permission denied
```

첫 번째는 sudo가 터미널을 요구한다는 단서이고, 두 번째는 스크립트 실행이 권한 문제로 거부됐다는 단서입니다.<br>
실패 단계가 같아도 확인할 설정이 달랐으므로, 다운로드 로그만 전달받은 사람이 원인을 파악하려면 ADMIN의 요약 확인이 추가로 필요했습니다.

이 문제를 겪고 나니 기준이 분명해졌습니다.

> 실패 단계가 같더라도 원인에 따라 확인할 곳은 달랐습니다. 운영자가 접근할 수 있는 기록에 어떤 정보가 있는지도 중요했습니다.

실패 상태와 단계, 요약에 남긴 원인은 문제를 분류하는 데 도움이 됐습니다.<br>
다만 이 글에서 다루는 버전에서는 다운로드 로그만으로 직접 원인을 확인할 수 있다는 수준까지 이어지지는 않았습니다.<br>
다운로드 로그에 포함할 원인 정보와 민감 정보 마스킹, 조회 권한의 범위를 함께 정리하는 것은 남은 개선 과제입니다.

<br>

### Apache 기반 Blue-Green 배포 붙이기

초기 SSH 배포는 기존 프로세스를 종료하고 새 프로세스를 띄우는 방식이었습니다.<br>
구조는 단순했지만, 전환 중 공백이 생길 수 있었습니다.<br>
프로세스를 종료한 뒤 새 버전이 뜨고 헬스 체크를 통과하기 전까지는 사용자가 503을 만날 가능성이 있었습니다.

이를 줄이기 위해 Apache reverse proxy를 기준으로 Blue-Green 배포를 붙였습니다.<br>
서비스마다 BLUE 포트와 GREEN 포트를 두고, 현재 active color가 아닌 포트에 새 버전을 먼저 띄웁니다.<br>
그 다음 내부 헬스 체크를 통과하면 Apache proxy를 새 포트로 전환하고, 외부 헬스 체크까지 확인한 뒤 이전 포트를 정리하는 흐름입니다.

개념적으로는 다음 순서입니다.

1. 현재 active color 확인
2. inactive 포트에 새 버전 실행
3. 내부 헬스 체크 3회 연속 성공 확인
4. Apache proxy 설정 전환
5. Apache reload
6. 외부 헬스 체크 확인
7. 외부 헬스 체크 실패 시 이전 active proxy로 복원
8. 성공 시 active color 갱신
9. drain 대기 후 이전 포트 정리

여기서 조심한 점은 "완전한 무중단 배포를 구현했다"고 말하지 않는 것이었습니다.<br>
제가 만든 것은 무중단을 수학적으로 보장하는 시스템이 아니라, Apache 전환과 헬스 체크, drain 대기를 통해 503 노출 가능성을 줄이는 구조에 가깝습니다.<br>
운영 글에서는 이 차이를 정확히 표현하는 것이 중요하다고 생각했습니다.

처음에는 단발 헬스 체크로 충분해 보였습니다.<br>
하지만 실제 운영에서는 일시적으로 응답이 성공할 수도 있고, 반대로 기동 직후 잠깐 흔들릴 수도 있습니다.<br>
그래서 내부 헬스 체크는 3회 연속 성공을 기준으로 두었고, 전환 후에는 public endpoint도 확인했습니다.

서비스마다 `/health`가 있는 것도 아니었습니다.<br>
어떤 서비스는 기본 `/` 경로만 확인할 수 있었고, 어떤 서비스는 내부 통신이 HTTP가 아니라 자체 HTTPS로 떠 있었습니다.<br>
그래서 헬스 체크 URL을 고정하지 않고 서비스별로 명시할 수 있게 했습니다.

#### 실패 시점에 따라 복구 방식 나누기

실패 시 필요한 조치는 전환 시점에 따라 달랐습니다.<br>
어느 단계에서 실패했는지에 따라 기존 서비스에 미치는 영향과 복구 방식도 구분했습니다.

| 실패 시점 | 기존 서비스 상태 | 처리 방식 |
| --- | --- | --- |
| inactive 프로세스 기동 또는 내부 헬스 체크 | 기존 active 프로세스와 proxy를 변경하지 않음 | 새 프로세스가 DeployX가 기동한 대상인지 확인한 뒤 inactive 프로세스만 정리 |
| Apache proxy switch | 기존 active 프로세스는 계속 실행 중 | configtest 실패 시 기존 설정 파일을 복원하고 reload하지 않음. 다만 파일 생성이나 권한 오류 등 일부 경로에서는 자동 복원이 보장되지 않음 |
| Apache reload | 기존 active 프로세스는 계속 실행 중 | `systemctl reload`와 `apachectl graceful`이 모두 실패하면 `RELOAD_APACHE`로 기록하며, proxy 설정의 자동 복원은 수행하지 않음 |
| 외부 헬스 체크 | 기존 active 프로세스를 아직 중지하지 않은 상태 | 기존 active proxy 설정을 복원하고 Apache를 reload한 뒤 inactive 프로세스를 정리 |
| 전환 완료 후 이전 프로세스 cleanup | 신규 active가 이미 트래픽을 처리하는 상태 | stop script의 비정상 종료는 경고로 남기고 배포는 성공 처리. SSH 실행 자체가 예외로 실패하면 배포 실패가 될 수 있음 |

이 구분에서 중요한 점은 외부 헬스 체크가 끝날 때까지 기존 active 프로세스를 종료하지 않는다는 것입니다.<br>
전환 후 외부 헬스 체크가 실패하면 기존 proxy 설정을 복원하고 Apache를 다시 reload할 수 있도록 이전 프로세스를 남겨두었습니다.<br>
이때 public health 실패 자체는 `TIMEOUT / CHECK_PUBLIC_HEALTH`, proxy 복원 script 실패는 `PROXY_SWITCH_FAILED / SWITCH_APACHE_PROXY`, Apache reload 실패는 `PROXY_SWITCH_FAILED / RELOAD_APACHE`로 구분했습니다.

반면 proxy switch와 Apache reload 구간은 모든 실패 경로에서 자동 복구가 보장되는 것은 아닙니다.<br>
특히 Apache reload가 실패하면 기존 active 프로세스는 살아 있어도 proxy 설정을 자동으로 되돌리지 않으므로, 이 상태를 복구 완료로 간주하지 않았습니다.<br>
일반 배포 과정의 복구가 실패하면 배포 상태는 `FAILED`로 남기고, 사용자가 명시적으로 실행한 rollback 자체가 실패한 경우에는 `ROLLBACK_FAILED`로 구분했습니다.

결국 이 흐름은 모든 실패를 하나의 rollback으로 처리하는 구조가 아닙니다.<br>
proxy 전환 전에는 기존 active를 건드리지 않고, public health 실패에는 명시적인 proxy 복원을 수행하며, 자동 복원이 보장되지 않는 전환·reload 실패는 운영자가 실패 지점을 바로 식별할 수 있게 남기는 구조에 가깝습니다.

#### 실제 로그로 확인한 실패 경로와 정상 완료 경로

구현한 흐름이 실제 배포에서 어떻게 동작하는지는 서로 다른 두 번의 배포 기록으로 확인했습니다.<br>
두 기록은 같은 배포를 재시도한 전후 비교가 아니라, 운영 과정에서 각각 관찰한 Apache proxy 전환 실패 경로와 정상 완료 경로입니다.

먼저 proxy 전환에 실패한 배포에서도 새 버전은 inactive GREEN 포트에서 내부 헬스 체크를 세 번 연속 통과했습니다.

```text
[Blue-Green] internal health check passed (3/3 consecutive successes).
[Blue-Green] Switching Apache proxy to GREEN on port <GREEN-target-port>...
[Blue-Green] Cleaning up target port <GREEN-target-port> after SWITCH_APACHE_PROXY...
[Blue-Green] Target port <GREEN-target-port> cleanup completed.
```

이 기록으로 JAR 업로드나 새 프로세스 기동이 아니라 Apache proxy를 전환하는 단계에서 흐름이 중단됐다는 사실을 좁힐 수 있었습니다.<br>
다만 `after SWITCH_APACHE_PROXY`라는 단계명은 남아 있어도, ADMIN이 확인하는 상단 요약의 실제 오류 원인은 다운로드 로그에서 빠져 있었습니다.<br>
따라서 이 발췌만으로 직접 원인이나 기존 BLUE proxy의 유지 여부까지 확인할 수는 없었고, 관찰 가능한 결과는 proxy 전환 단계에서 중단된 뒤 GREEN 프로세스가 정리됐다는 사실까지였습니다.

다른 정상 배포에서는 active GREEN을 유지한 상태에서 새 버전을 inactive BLUE 포트에 먼저 띄웠습니다.<br>
내부 헬스 체크가 세 번 연속 성공한 뒤 Apache proxy switch와 reload가 순서대로 완료됐습니다.

```text
[Blue-Green] internal health check passed (3/3 consecutive successes).
[Blue-Green] Switching Apache proxy to BLUE on port <BLUE-target-port>...
[Blue-Green] Apache proxy switch script completed.
[Blue-Green] Reloading Apache...
[Blue-Green] Apache reload completed.
```

전환 이후에는 사용자가 접근하는 public endpoint를 다시 확인했습니다.<br>
외부 헬스 체크가 세 번 연속 성공한 뒤에만 active color를 BLUE로 갱신했고, 30초 동안 connection drain을 기다린 다음 이전 GREEN 프로세스를 정리했습니다.

```text
[Blue-Green] public health check passed (3/3 consecutive successes).
[Blue-Green] Active color updated to BLUE.
[Blue-Green] Waiting 30s before stopping previous process to allow Apache connection drain.
[Blue-Green] Previous process cleanup completed.
```

원본 로그의 시각을 기준으로 각 단계의 소요 시간도 확인했습니다. 아래 시각은 모두 2026년 6월 26일 UTC 기준이며, 위 발췌에서는 가독성을 위해 시각을 생략했습니다.

| 구간 | 시작 | 완료 | 소요 시간 |
| --- | --- | --- | --- |
| 내부 헬스 체크 | 06:43:58.457 | 06:44:16.616 | 약 18초 |
| proxy switch와 Apache reload | 06:44:16.617 | 06:44:17.629 | 약 1초 |
| 외부 헬스 체크 | 06:44:17.630 | 06:44:25.079 | 약 7.5초 |
| 배포 시작부터 이전 프로세스 정리까지 | 06:43:52.344 | 06:44:55.523 | 약 63초 |

이를 통해 새 버전 기동, 내부 확인, proxy 전환, 외부 확인, drain, 이전 프로세스 정리가 의도한 순서대로 실행되는 것을 확인했습니다.<br>
다만 이 기록만으로 모든 요청에서 503이 전혀 발생하지 않았다고 단정할 수는 없으므로, 성공 로그는 완전한 무중단의 증명이 아니라 설계한 전환 순서가 실제로 수행됐다는 검증으로 해석했습니다.

<br>

### 레거시 서버 권한 차이를 설정으로 흡수하기

Blue-Green을 붙이면서 가장 현실적인 문제는 권한이었습니다.<br>
Apache proxy 전환 스크립트와 reload는 서버 권한에 민감합니다.<br>
어떤 서버는 배포 계정으로 바로 실행할 수 있었고, 어떤 서버는 `sudo -n`이 필요했습니다.

처음에는 NOPASSWD가 필요한 서버를 해결하려고 Apache 관련 명령에 일괄적으로 `sudo -n`을 붙였습니다.<br>
그런데 이 변경이 기존에 sudo 없이 잘 동작하던 서버에서는 오히려 실패를 만들었습니다.<br>
레거시 환경에서는 모든 서버가 같은 권한 모델을 갖고 있다고 가정하면 안 된다는 사실을 다시 확인한 순간이었습니다.

결국 `sudo -n` 사용 여부를 애플리케이션 코드의 조건문으로 처리하지 않고, 호스팅 서버 단위 설정으로 옮겼습니다.

- `hosting_servers.apache_sudo_mode`
- 기본값은 `NONE`
- `NOPASSWD`인 서버에서만 Apache switch/reload/precheck에 `sudo -n` 적용
- 서비스는 호스팅 서버 설정을 상속
- 호스팅 서버 수정 UI에서 Apache sudo mode 관리

이 설계가 더 자연스러웠던 이유는 Apache 실행 권한이 개별 서비스의 성질이라기보다 호스팅 서버의 성질에 가깝기 때문입니다.<br>
설정은 가장 자연스러운 소유 경계에 있어야 합니다.<br>
그래야 나중에 서버가 늘어나거나 권한 정책이 바뀌어도 코드가 아니라 데이터 설정으로 흡수할 수 있습니다.

<br>

## 누가 배포했는지 통제하고 증명할 수 있어야 했다

배포 과정이 안정되어도 접근 가능한 사람이 곧바로 운영 배포를 실행할 수 있다면 책임 경계는 여전히 모호했습니다.<br>
두 번째 전환점에서는 실행 권한을 역할과 승인 흐름으로 통제하고, 사용자와 관리 작업의 상태를 나중에도 확인할 수 있게 만드는 데 집중했습니다.

### 인증, RBAC, 승인 요청으로 배포 권한 통제하기

초기 도구에서는 접근 가능한 사람이 곧 배포 가능한 사람이었습니다.<br>
개인 도구나 실험용 도구라면 이 정도로도 충분할 수 있습니다.<br>
하지만 운영 도구가 되려면 사용자, 역할, 세션, 감사 로그, 승인 요청이 필요합니다.

그래서 역할을 `ADMIN`, `OPERATOR`, `VIEWER`로 나누었습니다.

- `ADMIN`: 사용자 관리, 설정 관리, 승인 및 배포 가능
- `OPERATOR`: 배포 요청 가능, 권한에 따라 즉시 배포 가능
- `VIEWER`: 조회 중심 접근

특히 중요한 변화는 OPERATOR의 배포 버튼이 항상 즉시 배포로 이어지지 않게 한 점입니다.<br>
일반 OPERATOR가 배포를 누르면 승인 요청이 생성됩니다.<br>
ADMIN 또는 긴급 배포 권한이 있는 OPERATOR만 즉시 배포할 수 있습니다.

모든 OPERATOR에게 즉시 배포 권한을 주면 승인 절차의 의미가 약해집니다.<br>
반대로 모든 배포에 ADMIN 승인을 요구하면 서비스 장애처럼 빠르게 배포해야 하는 상황에서 골든타임을 놓칠 수 있습니다.<br>
그래서 역할을 하나 더 늘리는 대신, 제한된 OPERATOR에게만 승인 절차를 건너뛸 수 있는 긴급 배포 권한을 서브 권한으로 부여했습니다.<br>
사용자 관리와 설정 변경 같은 ADMIN 권한 전체를 넘기지 않고 긴급 배포 가능 범위만 분리하려는 선택이었습니다.

{% include diagrams/deployx-approval.html %}

이렇게 바꾸면 배포 버튼 하나에도 조직의 권한 정책이 들어갑니다.<br>
누가 요청했고, 누가 승인했으며, 어떤 서비스의 어떤 버전이 배포되었는지를 남길 수 있습니다.<br>
승인 요청 생성 시 관리자에게 메일을 보내고, 승인 후 배포 결과는 요청자와 승인자 모두에게 발송하도록 했습니다.

승인 요청은 생성 시점의 대상 버전을 보관합니다.<br>
승인을 기다리는 동안 새 버전이 등록되더라도, 기존 요청을 승인하면 요청 당시 선택한 버전이 배포 대상이 됩니다.<br>
실제 배포를 시작할 때는 앱 단위의 `is_busy` 상태를 확인해 같은 앱의 배포가 동시에 실행되지 않도록 했습니다.

다만 승인 대기 요청 자체의 중복 처리와 승인·실행 상태의 일관성은 별도의 문제였습니다.<br>
이 부분은 이후 고도화에서 승인 요청의 생명주기와 함께 다시 정리할 과제로 남겼습니다.

세션 방식도 정리했습니다.<br>
API용 Bearer 토큰과 운영 UI용 쿠키 세션을 분리했습니다.<br>
도구가 커질수록 인증 방식이 흐릿하게 섞이는 것은 위험하다고 봤습니다.

<br>

### 사용자 초대와 비밀번호 설정 흐름

사용자 관리에서도 운영 정책을 반영했습니다.<br>
DeployX는 공개 회원가입을 받는 서비스가 아니기 때문에, ADMIN이 사용자를 생성하는 방식을 유지했습니다.<br>
다만 ADMIN이 초기 비밀번호를 알 필요는 없도록 만들고 싶었습니다.

그래서 사용자는 비밀번호 없이 생성됩니다.<br>
이후 이메일의 설정 링크를 통해 본인이 비밀번호를 설정해야 로그인할 수 있습니다.<br>
`password_set_at`이 없으면 로그인 불가 상태로 처리했습니다.

이 기능에서도 작은 운영 버그를 겪었습니다.<br>
비밀번호 해시는 저장되었지만 `password_set_at`이 기록되지 않아 사용자가 계속 `PASSWORD_PENDING` 상태로 남는 문제가 있었습니다.<br>
비밀번호가 저장됐다는 사실만으로 계정 상태를 판단하면 안 된다는 것을 배웠습니다.

이후에는 비밀번호 설정 완료 시각, 토큰 만료, 로그인 허용 여부를 함께 보도록 정리했습니다.<br>
비밀번호 설정 메일 재발송 기능도 추가했습니다.<br>
운영에서는 사용자가 메일을 놓치거나 토큰이 만료되는 일이 충분히 생기기 때문입니다.

로그인한 사용자가 비밀번호를 변경할 때는 현재 비밀번호를 검증하고, 저장 후 새 비밀번호로 실제 검증까지 한 번 더 수행했습니다.<br>
응답만 성공으로 내려주는 것보다, DB에 반영된 결과를 다시 확인하는 편이 운영 버그를 줄이는 데 도움이 됐습니다.

<br>

### 감사 로그와 검색 UX 다듬기

운영자는 배포 이력만 보는 것이 아닙니다.<br>
누가 사용자를 만들었는지, 누가 권한을 바꿨는지, 누가 승인 요청을 처리했는지도 확인해야 합니다.<br>
그래서 감사 로그 API와 UI를 추가했습니다.

감사 로그는 ADMIN과 OPERATOR가 조회할 수 있게 했습니다. 앞서 설명한 실패 원인 요약의 ADMIN 전용 접근과는 구분되는 권한입니다.

감사 로그에는 로그인과 로그아웃, 사용자 생성과 권한 변경, 승인 요청 생성·승인·거절, CI 산출물 업로드, 배포 실행처럼 사용자가 시스템에 남긴 행위를 기록했습니다.<br>
긴급 배포 권한을 부여하거나 해제하는 행위도 `USER_EMERGENCY_DEPLOY_UPDATE`로 남겼습니다.

여기서 감사 로그와 배포 로그의 역할은 구분했습니다.<br>
감사 로그의 `DEPLOY_TRIGGER`는 누가 배포를 실행했는지를 남기고, 헬스 체크나 proxy switch 같은 상세 단계와 최종 결과는 배포 로그가 담당합니다.<br>
따라서 감사 로그는 행위의 주체와 시점을 추적하는 기록이고, 배포 로그와 결과 메일은 배포 과정과 실패 원인을 진단하는 기록에 가깝습니다.

아직 남은 한계도 있습니다.<br>
ADMIN의 직접 배포와 긴급 권한을 가진 OPERATOR의 즉시 배포가 모두 `DEPLOY_TRIGGER`로 기록되기 때문에, 행위 타입만으로는 긴급 권한이 실제 사용된 배포인지 구분할 수 없습니다.<br>
현재는 행위 주체와 승인 요청·메일 기록을 함께 대조해야 하므로, 긴급 배포 사용 자체를 별도 action이나 속성으로 남기는 보완이 필요합니다.

처음에는 전체 목록을 보여주는 방식이 가장 빠릅니다.<br>
하지만 운영 데이터는 반드시 쌓입니다.<br>
데이터가 쌓이면 전체 목록은 곧 사용할 수 없는 화면이 됩니다.

그래서 감사 로그와 대시보드 검색에 날짜 범위를 추가했습니다.<br>
기본값은 최근 7일로 두고, 종료일은 사용자가 선택한 날짜의 `23:59:59`까지 포함되도록 보정했습니다.<br>
또 결과가 많아질 것에 대비해 페이지 나누기(pagination)을 넣고, 페이지 크기는 20, 50, 100개 중 선택할 수 있게 했습니다.

작은 UX도 같이 손봤습니다.<br>
예를 들어 주기적 갱신(polling) 중 화면이 깜빡이는 문제는 기능 버그는 아니지만, 운영자가 계속 켜두는 화면에서는 꽤 거슬립니다.<br>
운영 도구의 UX는 화려함보다 안정감이 중요했습니다.<br>
검색 조건이 유지되고, 페이지 이동이 예측 가능하고, 로그 다운로드가 필요한 시점에 바로 되는 것이 더 중요했습니다.

<br>

## 기존 도구와 연결하되 실패를 함부로 전파하지 않아야 했다

운영 가능한 도구가 된다는 것이 빌드와 알림까지 모든 책임을 DeployX 안으로 가져온다는 뜻은 아니었습니다.<br>
세 번째 전환점에서는 기존 CI가 만든 산출물을 안전하게 이어받고, 알림 실패가 배포 결과로 전파되지 않게 하며, 배포 전략과 로그를 DB에 남기는 기준을 분명히 했습니다.

### CI 산출물 연동: 빌드와 배포의 경계 나누기

DeployX가 빌드 시스템까지 직접 구현할 필요는 없다고 판단했습니다.<br>
이미 팀마다 Jenkins, GitHub Actions, GitLab CI 같은 도구를 쓰고 있을 수 있습니다.<br>
DeployX가 그 역할을 모두 대체하려고 하면 범위가 너무 커집니다.

대신 외부 CI에서 만들어진 JAR 산출물을 안전하게 받아 배포 대상으로 등록할 수 있게 했습니다.<br>
빌드는 CI가 하고, 운영 배포 통제는 DeployX가 맡는 구조입니다.

CI 연동을 위해 토큰 관리도 추가했습니다.

- CI 토큰은 생성 시 한 번만 원문 표시
- DB에는 해시로 저장
- 앱 단위 scope 적용
- 만료 정책 적용
- 필요하면 1회 사용 정책 적용
- Git branch, commit SHA, build number, provider, run URL 저장

각 정책이 막으려는 문제는 달랐습니다.<br>
앱 단위 scope는 특정 앱용 토큰으로 다른 앱의 산출물을 등록하는 것을 막고, 만료 정책은 유출된 토큰이 장기간 사용되는 범위를 줄입니다.<br>
1회 사용 정책은 토큰이 정상 사용된 뒤 다시 사용되는 replay 가능성을 제한합니다.<br>
다만 탈취한 사람이 정상 CI보다 먼저 유효한 요청을 보내는 상황까지 막는 것은 아니므로, 1회용이라는 이유만으로 안전하다고 보지는 않았습니다.

1회용 토큰의 소비 시점도 명확히 정했습니다.<br>
인증, 앱 scope, 요청 검증을 통과하고 CI 업로드 세션 생성 트랜잭션이 commit되면 토큰을 사용한 것으로 처리합니다.<br>
세션 생성 자체가 실패하면 토큰 소비도 rollback되지만, 세션을 만든 뒤 실제 파일 업로드나 finalize에 실패하면 토큰은 이미 소모된 상태입니다.<br>
따라서 새 업로드 세션을 만들어 다시 시작하려면 새 토큰이 필요합니다.<br>
이는 새 세션 생성에 사용하는 토큰의 재사용 제한이며, 기존 세션에서 파일 업로드나 finalize를 재시도할 수 있는지와는 별개의 문제입니다.

이렇게 해두면 특정 commit SHA가 어떤 배포 이력으로 이어졌는지 추적할 수 있습니다.<br>
장애가 났을 때 "어떤 빌드가 어느 서버에 언제 배포됐는가"를 확인할 수 있는 근거가 생깁니다.

이 경계 설정이 중요했습니다.<br>
DeployX는 CI/CD 전체를 혼자 다 하려는 도구가 아니라, 외부 CI 산출물을 받아 운영 배포를 통제하는 CD 도구에 가깝습니다.<br>
그 덕분에 기존 CI를 살리면서도 운영 배포 단계의 권한, 승인, 감사, 알림을 DeployX에서 관리할 수 있었습니다.

<br>

### 알림은 작업 흐름의 일부다

처음에는 메일 알림이 부가 기능처럼 느껴졌습니다.<br>
하지만 승인 기반 배포에서는 알림이 작업 흐름의 일부였습니다.<br>
승인 요청이 생성됐는데 관리자가 모르면 배포는 진행되지 않습니다.<br>
승인 후 배포가 실패했는데 요청자에게 전달되지 않으면, 다시 누군가 화면에 들어와 확인해야 합니다.

그래서 다음 알림을 추가했습니다.

- 승인 요청 생성 시 ADMIN에게 메일 발송
- 배포 성공/실패 결과 메일 발송
- 승인 후 배포 결과를 요청자와 승인자 모두에게 발송
- 실패 시 failure cause와 script log 첨부
- 첨부 로그에서 password/token/secret/key 계열 키워드로 식별한 값 마스킹

다만 SMTP 실패가 배포 자체를 실패시키지는 않도록 했습니다.<br>
알림은 중요하지만, 메일 서버의 일시적 문제 때문에 이미 성공한 배포를 실패로 뒤집는 것은 더 큰 혼란을 만들 수 있습니다.<br>
그래서 알림은 best-effort로 처리하고, 배포 결과 메일은 수신자별 알림 로그를 남기도록 했습니다.

이 기록은 배포 결과 메일의 발송 시도와 실패 원인을 확인하는 용도입니다.<br>
여러 수신자에게 한 번에 발송한 결과를 수신자별로 남기므로 개별 전달 여부까지 증명하지는 않습니다.<br>
승인 요청 메일과 발송을 건너뛴 경우는 기록 대상에 포함하지 않았으며, 자동 재시도와 실제 메일의 중복 발송 방지도 남아 있는 개선 과제입니다.

<br>

### DB에 남기는 기준 데이터와 로그 마스킹

서버, 서비스, 버전, 배포 이력은 이미 DB 기준으로 관리되고 있었으므로, 기준 데이터가 한곳에 있어야 한다는 원칙은 처음부터 명확했습니다.<br>

고도화하면서 새로 필요해진 것은 배포 전략 스키마였습니다.<br>
Blue-Green을 붙이는 순간, "이 서비스는 어떤 방식으로 배포되는가"와 "그 전환을 누가 어떻게 제어하는가"를 DB가 설명할 수 있어야 했습니다.<br>
기존 서비스 스키마는 서비스가 무엇인지를 담는 구조였고, 배포 전략 스키마는 그 서비스를 어떻게 운영할지를 담는 구조였습니다.

이 경계를 정리하는 것이 생각보다 중요했습니다.<br>
배포 전략 스키마가 담아야 할 범위를 명확히 하지 않으면, 배포 방식과 서비스 정보가 뒤섞여 나중에 전략만 바꾸거나 서비스 정보만 수정하는 것이 어려워집니다.<br>
그래서 배포 방식, 프록시 전환 방식, 헬스 체크 기준처럼 배포 실행 시점에 참조하는 값들을 이 스키마의 소유로 두기로 했습니다.

또 하나 크게 고민했던 부분은 배포 로그를 DB에 저장할 때 민감 정보 처리였습니다.<br>
배포 스크립트 실행 로그에는 환경변수, 연결 문자열, 토큰이 섞여 들어올 수 있습니다.<br>
로그를 그대로 저장하면 DB 조회만으로도 민감 정보가 노출될 수 있었습니다.<br>
그래서 다운로드용 로그를 DB에 저장하기 전과 결과 메일에 로그를 첨부할 때, password/token/secret/key 계열 키워드로 식별한 값을 마스킹해 민감 정보 노출 가능성을 줄였습니다.<br>
다만 키워드로 식별하는 방식이므로, 알려지지 않은 키 이름이나 예상하지 못한 출력 형식에 포함된 값까지 모두 가려진다고 보장할 수는 없습니다.<br>
마스킹은 현재 식별 가능한 형식의 노출을 줄이는 범위로 적용했습니다.

<br>

## 마무리

이번 작업의 출발점은 내부 배포를 더 편하게 진행하고 싶다는 것이었습니다.<br>
사용하면서 실패 원인이 보이지 않거나, 서버마다 권한 설정이 다르거나, 배포 승인이 필요한 상황을 만났고 그때마다 필요한 부분을 하나씩 보완했습니다.

실제 배포 로그에서는 새 버전의 내부 확인부터 Apache 전환, 외부 응답 확인, 이전 프로세스 정리까지 의도한 순서로 완료되는 것을 확인했습니다.<br>
실패 로그에서는 전환 단계는 알 수 있어도 실제 오류 원인이 빠지면 운영자가 다시 확인해야 한다는 점을 배웠습니다.<br>
제게 배포의 편의성은 실행 버튼을 누르는 순간뿐 아니라, 배포 전후에 필요한 정보를 쉽게 확인하는 데까지 이어졌습니다.

승인 요청의 중복 처리와 승인·실행 상태의 일관성은 이후 고도화에서 이어서 다룰 예정입니다.<br>
앞으로도 현재 서버 환경과 운영자의 사용 방식에 맞춰, 실제 배포에서 불편했던 지점을 기준으로 개선해가려고 합니다.

> 내부 배포를 편하게 만드는 일에는 배포 전후의 판단 근거와 책임 경계를 남기는 일도 포함되어 있었습니다.

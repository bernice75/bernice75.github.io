## 1. 사내 첫 푸시는 왜 필요했나

최근 매장 운영 시스템에 사내 첫 앱 푸시를 도입했습니다.<br>
무인 키오스크에서 결제 모듈이나 프린터, 카메라 같은 하드웨어 장치에 문제가 생기면 매장 담당자에게 알릴 수단이 필요해졌기 때문입니다.<br>
앱이 설치된 담당자의 휴대폰으로 알리고, 담당자 앱의 수신이 확인되지 않으면 그룹 매니저에게 다시 알리는 시스템으로 설계했습니다.

처음에는 단순하게 알림을 발행한 후 Firebase Cloud Messaging(FCM)에 메시지를 전달하는 정도의 역할이면 된다고 생각했습니다.<br>
그러나 실제로 필요한 것은 메시지를 보내는 것을 넘어 **누가 받아야 했고, 어느 앱이 실제로 수신했으며**, 수신이 확인되지 않았을 경우 무엇을 할지 설명할 수 있는 방안이었습니다.

![실제 기기에 도착한 테스트 알림]({{ site.baseurl }}/assets/img/posts/2026-08-12-app-push/app-notification.png)

기존에 존재하던 관리자 웹, 사용자 앱, 키오스크의 세 서비스가 유기적으로 연결될 수 있는 중앙 푸시 서버 하나를 구축하는 것이 이번 도입의 목표였습니다.<br>  
설계에 들어가면서, 각 서비스가 푸시 서버를 호출하는 목적과 푸시 서버의 역할을 점검했습니다. 


| 서비스   | 푸시 시스템에서 하는 일               |
| ----- | --------------------------- |
| 관리자 웹 | 임의로 캠페인을 생성하고 발송하는 유일한 창구   |
| 키오스크  | 자기 매장의 장애를 감지해 캠페인을 생성하고 발송 |
| 사용자 앱 | 알림 수신과 수신 확인 전송             |
| 푸시 서버 | 구독·동의·캠페인·발송 이력·에스컬레이션 관리   |

푸시 서버를 공통 호출부로 사용하므로, 가장 먼저 시작한 설계는 호출 주체에 대한 구분이었습니다.<br>

관리자 웹과 사용자 앱은 공유된 비밀키를 사용해 각자 JWT를 직접 발급하고, 사람이 로그인하지 않는 키오스크는 이미 등록된 매장 공인 IP를 대조했습니다. 같은 `manager`라도 관리자 웹 사용자는 발송할 수 있고 앱의 매니저는 받기만 하므로, 사용자 유형 뿐 아니라 토큰의 발급처까지 권한 경계로 삼았습니다.<br>

또한 필수 알림은 담당자가 수신하지 못할 경우 매니저에게 대리 통지되어야 한다는 정책이 있었습니다.<br>

이를 보장하기 위해 FCM 전달 결과와 별개로 앱이 직접 수신 확인(ACK)을 응답하도록 했습니다. 이 글에서 ACK는 사용자의 열람 확인이 아니라, 앱의 **FCM 수신 콜백**에서 확인 엔드포인트를 호출해 남기는 앱 수신 확인을 뜻합니다.<br>
서버는 전달 시각과 앱 수신 확인 시각을 구분해 저장하고, 60초 주기 배치를 통해 전달 후 120초가 지나도 ACK가 없는 알림을 감지하여 최악의 경우 약 3분 내에 그룹 매니저에게 대리 통지를 발송하도록 했습니다.

여기까지가 뒤의 숫자를 읽기 위해 필요한 시스템 설명의 전부입니다.<br>이제 14일 간 운영하며 기록된 내용으로 넘어갑니다.

## 2. 서버 기준으로는 완벽했던 14일

배포 후 2026년 7월 27일부터 8월 10일까지 데이터를 집계했습니다.<br>
이 기간에 키오스크가 만든 캠페인은 1,314건이었고, 1차 수신자에게 실제로 전달된 건은 1,253건이었습니다.


| 항목             | 값      |
| -------------- | ------: |
| 집계 기간          | 14일    |
| 키오스크가 만든 캠페인   | 1,314건 |
| 실제 전달된 1차 수신 건 | 1,253건 |
| FCM 전송 실패      | **0건** |
| dry-run 오염     | 0건     |


FCM 전송 실패는 한 건도 없었습니다.<br>서버가 아는 범위에서는 요청을 받고, 대상을 찾고, FCM에 메시지를 전달하는 과정이 모두 성공했습니다. 대시보드를 전송 성공률만으로 만들었다면 모든 지표가 초록불이었을 것입니다.

다만 이때 사용자 앱은 아직 정식 배포 전이었고 내부 테스트 단계였습니다.<br>
따라서 이 수치를 완성된 서비스의 성과 지표로 볼 수는 없습니다. 대신 부분 배포 상태에서도 서버가 무엇을 알고 무엇을 모르고 있었는지는 확인할 수 있었습니다.

<br>

## 3. 그런데 확인율은 2.0%였다

전달 결과 옆에 앱 수신 확인 수를 놓자 그림이 달라졌습니다.<br>1,253건 가운데 앱 수신이 확인된 것은 단 25건, **2.0%**뿐이었습니다.

관리자 화면에서도 같은 차이가 보였습니다. 아래 두 캠페인은 모두 상태가 `FCM 전달 성공`입니다. 하나는 담당자 앱에서 ACK가 왔고, 다른 하나는 ACK가 오지 않아 에스컬레이션까지 발동했습니다.


| 담당자 앱의 수신이 확인된 캠페인                                                                                           | 전달됐지만 앱 수신이 확인되지 않은 캠페인                                                                                                  |
| ----------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| ![FCM 전달 후 담당자 앱의 ACK가 기록된 캠페인]({{ site.baseurl }}/assets/img/posts/2026-08-12-app-push/campaign-acknowledged.png) | ![FCM 전달에는 성공했지만 담당자 앱의 ACK가 기록되지 않은 캠페인]({{ site.baseurl }}/assets/img/posts/2026-08-12-app-push/campaign-unacknowledged.png) |


FCM의 성공 응답은 FCM이 메시지를 접수했다는 뜻입니다.<br>
기기가 오프라인일 수도 있고, 운영체제 정책 때문에 전달이 늦어질 수도 있습니다. FCM 응답만으로는 앱이 메시지를 실제로 받았는지 알 수 없지만, 앱의 ACK를 함께 기록하면 **FCM에 보냈다**와 **앱이 받았다**를 구분할 수 있습니다. 다만 ACK는 백그라운드 수신 시점에 전송되므로, 사용자가 알림을 실제로 열어 봤는지까지 증명하지는 않습니다.

앱 수신 확인율 2.0%는 그 구분을 만들지 않았다면 존재하지 않았을 숫자였습니다.<br>
다만 이 숫자를 곧바로 “푸시 시스템이 실패했다”고 읽는 것도 틀렸습니다. 어느 매장에서 어떤 알림이 발생했는지 한 번 더 나눠봐야 했습니다.

<br>

## 4. 한 매장이 전체 전달의 97.6%를 만들고 있었다

매장과 용도별로 데이터를 나누자 이상치가 바로 드러났습니다.


| 구분                | 전달         | 앱 수신 확인 | 확인율  |
| ----------------- | ----------: | ------: | ----: |
| 실 운영 중 오작동한 기기 1대 | **1,223건** | **0건** | 0%   |
| 내부 테스트 기기 1대      | 16건        | 11건    | 69%  |
| 나머지 실 운영 기기 2대    | 14건        | 14건    | 100% |


한 매장이 전체 전달의 97.6%를 차지했습니다.<br>
해당 키오스크가 문제 상황을 잘못 판별해 같은 종류의 장애 알림을 반복해서 요청하고 있었습니다. 

키오스크의 오판독 로직은 8월 10일에 조치했으나, 여기서 중요한 것은 서버가 이 1,223건을 어떻게 봤느냐입니다.<br>
요청은 인증된 키오스크에서 왔고, 캠페인 생성과 대상 선정, FCM 전달도 모두 성공했습니다. 서버가 가진 지표 안에서는 오작동 매장의 1,223건과 실제 운영 매장의 14건이 똑같이 성공한 발송이었습니다.

> 서버는 “전송에 성공했는가”는 알았지만, “이 알림이 보낼 만한 것이었는가”는 몰랐다.

이상 발송을 알아챈 경로도 실시간 알림이 아니라 14일 뒤의 수동 집계였습니다.<br>
앱 수신 확인 시각을 전달 시각과 별도 컬럼으로 남기지 않았다면, 0%라는 이상 신호를 세어볼 수도 없었을 것입니다.

<br>

## 5. 이상치를 걷어내자 시스템은 정상으로 보였다

오작동 기기에서 발생한 이상치와 내부 테스트 데이터를 제외하면, 나머지 실 운영 기기 2대에서는 14건 모두 앱 수신이 확인됐습니다.<br>표본이 14건뿐이므로 확인율 100%를 성과로 내세울 수는 없습니다. 이 숫자가 지지하는 주장은 하나뿐입니다. **앱의 수신 확인 경로가 실제 운영 데이터에서도 채워지고 있었다**는 것입니다.

구독 상태도 함께 확인했습니다.<br>
이전에 같은 기기에서 계정을 바꿔 로그인하면 하나의 FCM 토큰에 두 계정의 구독이 동시에 활성화되는 문제가 있었습니다. 로그아웃 때 구독을 비활성화하고, 다음 로그인 때 같은 토큰 해시의 이전 구독을 다시 정리하도록 바꾼 뒤 운영 데이터에서는 토큰 6개 모두 활성 구독이 정확히 하나였습니다.

즉 겉보기 앱 수신 확인율 2.0%는 시스템 전체의 실패율이 아니었습니다.<br>
오작동 한 건이 전체 분포를 덮고 있었고, 그 이상치를 분리하자 수신 확인과 구독 정리는 의도한 대로 작동하고 있었습니다. 여기까지 확인하면 자연스럽게 다음 질문이 생깁니다.

<br>

## 6. 그렇다면 서버가 1,223건을 막았어야 했을까

처음 떠오르는 대응은 서버에 발송량 제한이나 중복 억제를 넣는 것 일겁니다.<br>
한 매장에서 짧은 시간에 같은 알림이 반복되면 일정 횟수 이후 차단하는 방식입니다.

하지만 이 시스템에서는 그렇게 하지 않았습니다.

키오스크가 보내는 것은 결제 모듈, 현금 장치, 프린터, 카메라처럼 반드시 확인해야 하는 하드웨어 장애 알림입니다. 서버가 횟수만 보고 버리기 시작하면, 실제로 장비가 연쇄 고장 나는 순간에 가장 필요한 알림이 사라질 수 있습니다.<br>
광고성 캠페인은 기본적으로 에스컬레이션하지 않지만 필수 캠페인은 막지 않도록 종류별 정책을 나눈 이유도 같습니다. “밤이라서 막지 않는다”와 “많이 와서 막지 않는다”는 같은 판단이었습니다.

키오스크가 임의의 사람에게 알림을 보낼 수 있게 둔 것은 아닙니다.<br>키오스크는 장애 내용만 전달하고, 대상 매장과 수신자 종류, 에스컬레이션 여부는 서버가 고정합니다. 이것은 사칭과 오배송을 막기 위한 대상 통제입니다. 

반면 발송량을 제한하는 것은 필수 알림을 버릴 수 있는 유량 통제입니다. 둘은 목적이 다르다고 판단했습니다.<br>이 판단은 “모든 요청을 무조건 믿는다”는 뜻도 아닙니다.<br>
오작동 판별 로직은 키오스크에서 수정했고, 키오스크에는 5분 cooldown이 있습니다. 다만 장애가 실제로 반복되는 상황과 클라이언트가 오판하는 상황을 서버가 횟수만으로 확정하지 않게 했습니다.

서버는 설계대로 1,223건을 전부 보냈습니다.<br>
문제는 서버가 막지 않았다는 사실보다, 사람이 그 이상을 너무 늦게 알았다는 사실에 있었습니다.

<br>

## 7. 부족했던 것은 억제가 아니라 관측이었다

필수 알림을 자동으로 버리지 않기로 했다면, 운영자가 이상을 빠르게 판단할 수 있어야 합니다.<br>
이번 시스템은 수신자 제외와 에스컬레이션에서는 이미 그 원칙을 일부 적용하고 있었습니다.

광고 미동의나 야간 미동의로 제외된 수신자를 대상 선정 단계에서 지우지 않고, `건너뜀` 상태와 사유를 남겼습니다.<br>
활성 수신자가 0명인 경우도 성공으로 넘기지 않았습니다. 캠페인을 실패 상태로 두고 매니저 에스컬레이션을 시도했으며, 매니저조차 없으면 “통지 대상 0명”이라는 증적을 남겼습니다.

![활성 구독이 없어 전송하지 못한 캠페인과 실패 사유]({{ site.baseurl }}/assets/img/posts/2026-08-12-app-push/campaign-failed.png)

```json
"escalation": {
  "triggered": true,
  "reason": "send_failed",
  "targetCount": 0,
  "sentCount": 0,
  "failedCount": 0,
  "note": "no active manager subscription found for this store group"
}
```

`targetCount`가 0이어도 `triggered`는 `true`입니다.<br>
아무도 받지 못한 사건을 없애지 않고, 알리려고 했으나 받을 사람이 없었다는 사실까지 남겼습니다.

실제 운영 기간에는 에스컬레이션이 1,665건 발동했습니다.


| 사유                | 발동     | 통지 성공 | 통지 대상 0명 |
| ----------------- | ------: | -----: | --------: |
| 전달됐지만 앱 수신 미확인    | 1,237건 | 0건    | 1,237건   |
| 전송 실패 또는 활성 구독 없음 | 428건   | 0건    | 428건     |


여기서 숫자가 맞지 않았습니다.<br>
전달 1,253건 중 최종 ACK는 25건이므로 끝내 앱 수신이 확인되지 않은 건은 1,228건이어야 합니다. 그런데 `ack_timeout` 에스컬레이션은 1,237건으로, **아홉 건이 더 많았습니다.**

에스컬레이션 발동 여부와 최종 ACK 여부를 두 축으로 나누자 차이의 정체가 드러났습니다.

| 에스컬레이션 | 최종 앱 수신 확인 | 건수 |
| -------- | ---------- | --: |
| 발동함      | 안 됨        | 1,228건 |
| 발동함      | 됨          | **9건** |
| 안 함       | 됨          | 16건 |
| 안 함       | 안 됨        | 0건 |

아홉 건은 에스컬레이션이 먼저 발동한 뒤 ACK가 도착한 경우였습니다. 반대로 ACK가 끝내 오지 않았는데 에스컬레이션도 발동하지 않은 건은 없었습니다. 안전망이 누락된 것은 아니었지만, 왜 확인된 건까지 먼저 미확인으로 판정됐는지는 설명해야 했습니다.

확인 지연을 추적하다가 `sent_at`과 `acked_at`이 서로 다른 시간대로 기록된 사실을 발견했습니다.

| 시각 | 기록 방식 | 시간대 |
| --- | ------ | --- |
| `sent_at` | 애플리케이션이 기록 | UTC |
| `acked_at` | DB의 `NOW()`로 기록 | KST |

두 시각을 그대로 빼면서 모든 확인 지연에 9시간이 더해졌습니다. 처음에는 평균 약 10.4시간, 최소 약 9.1시간으로 읽었지만, 9시간을 보정한 결과는 달랐습니다.

| 지표 | 기록값 | 보정값 |
| --- | ---: | ---: |
| 평균 앱 수신 확인 지연 | 약 10.4시간 | **약 1시간 23분** |
| 최소 앱 수신 확인 지연 | 약 9.1시간 | **약 4분 28초** |
| 최대 앱 수신 확인 지연 | 약 27.2시간 | **약 18시간 10분** |

시간대 혼용은 통계만 왜곡한 것이 아니었습니다. 미확인 감시 배치도 `sent_at`이 현재보다 120초 이상 과거인지 비교했기 때문에, UTC로 기록된 발송 시각을 이미 9시간 전의 값처럼 판단했습니다. 결과적으로 **120초 임계값은 사실상 작동하지 않았고, 미확인 판정은 발송 직후 내려지고 있었습니다.**

1,228건과 1,237건의 불일치는 계산 오류가 아니라 이 시간대 버그를 찾아낸 단서였습니다. 기록을 남기는 것만으로는 충분하지 않았습니다. 같은 사건을 나타내는 시각이 같은 기준으로 기록되는지까지 확인해야 했습니다.


통지 성공이 0건인 것은 이 기간에 대리 수신할 매니저가 앱으로 로그인하지 않았기 때문입니다.<br>
안전망은 발동했고, 받을 사람이 없다는 사실도 전부 기록됐습니다. 테스트 서버에서는 매니저 구독을 만든 뒤 대리 통지와 확인까지 이어지는 경로를 별도로 재현했습니다. 운영에서 성공한 사례처럼 섞이지 않도록 두 출처는 구분했습니다.

![테스트 서버에서 재현한 매니저 에스컬레이션 성공 화면]({{ site.baseurl }}/assets/img/posts/2026-08-12-app-push/campaign-escalated.png)

수집된 지표들을 확인하는 과정에서는 시간대 혼용 외에도 다음 세 가지 허점을 발견했습니다.

1. 관측은 상태값이 실제 사건과 일치할 때만 의미가 있습니다.

   초기에는 실제로 보내지 않은 dry-run을 편의상 `전달됨`으로 기록했습니다. 확인이 올 수 없는 건을 감시 배치가 모두 미확인으로 판정하자, 상태를 `건너뜀`으로 바꾸고 사유를 남겼습니다. 또 FCM 발송보다 이력 저장이 늦어 즉시 도착한 확인 요청이 404가 되던 경쟁 조건은, 발송 전에 수신 행을 `대기` 상태로 먼저 만들어 없앴습니다.

2. 매니저 확인도 처음에는 구조적으로 404였습니다.

   발송 이력은 사고가 난 하위 매장 기준인데 매니저 토큰은 그룹 대표 매장을 가리켜, 매장 조건을 포함한 확인 쿼리가 절대 일치할 수 없었습니다. 매니저는 캠페인과 전역 수신자 식별자로 확인하게 바꾸고, 두 에스컬레이션 경로가 같은 기록 함수를 사용하도록 통일했습니다.

3. 수치를 추적하면서 아직 남은 공백도 발견했습니다.

   현재 증적만으로는 “그룹은 찾았지만 매니저 구독이 없음”과 “그룹 해석 자체에 실패함”을 구분하기 어렵습니다. 일부 사유 문구는 실제로 매니저가 없는 상황을 그룹 해석 실패처럼 읽히게 했습니다. 로그를 남기는 것과 로그가 진실을 말하게 하는 것은 다른 일이었습니다.

반대로 기록 덕분에 설계가 실제로 회수된 사례도 있었습니다.
`send_failed` 에스컬레이션이 남은 캠페인 428건 중 약 364건은 구독이 다시 등록된 뒤 최근 48시간 실패분을 자동 재발송하는 경로로 회복됐습니다. 활성 수신자가 없던 캠페인을 성공으로 처리했다면, 나중에 담당자가 앱을 설치해도 이미 성공한 건으로 간주되어 다시 보내지 못했을 것입니다.

이제 추가해야 할 것은 필수 알림을 버리는 상한이 아니라, 매장별 발송량이 평소보다 급증할 때 운영자에게 드러나는 지표입니다.

> 필수 알림 경로에서 서버는 임의로 판단해 버리지 않는다. 대신 사람이 빠르게 판단할 수 있도록 보이게 한다.

## 8. 그리고 이 작업을 계약서로 위임했다

이 프로젝트는 1인 개발로 진행했습니다.<br>
푸시 서버의 설계와 구현, 검증, 서비스 간 계약 작성을 직접 맡고, 관리자 웹·키오스크·사용자 앱의 반영 작업은 서비스별 AI 에이전트 세션에 나누어 위임했습니다.

세 서비스의 기술 스택은 Spring Boot, Electron과 TypeScript, Flutter로 서로 달랐습니다.<br>
다른 저장소의 구현을 공유하는 대신 API와 인증 규칙을 적은 계약 문서를 인터페이스로 사용했습니다. 구현이 끝나면 완료 보고를 실제 코드·데이터와 대조했고, 마지막에는 직접 수동 QA를 했습니다.

계약 문서는 처음부터 존재한 것이 아닙니다.<br>
푸시 서버가 어느 정도 완성된 뒤 다른 서비스에 연계 작업을 전달하기 위해 작성했습니다. 이미 코드와 머릿속에 있던 것을 밖으로 꺼내 적다 보니 타입과 경로처럼 눈에 보이는 것은 잘 적혔지만, 작성자에게 자명한 의미가 빠졌습니다.

가장 대표적인 예가 구독 등록이었습니다.<br>
계약에는 API 경로와 파라미터와 응답이 있었지만, “이 API는 토큰 저장이 아니라 현재 계정과 기기의 바인딩을 갱신하는 행위”라는 설명이 없었습니다. 앱은 FCM 토큰이 이미 있으면 등록을 생략하도록 구현이 진행됐습니다. 토큰 등록 API라는 전제에서는 합리적인 최적화였으나, 새로 등록된 계정에 토큰이 바인딩되지 않아 새 계정으로는 알림이 오지 않았습니다.

결국 계약에 다음 문장을 추가했습니다.

> 재등록 조건은 토큰이 새로 발급됐을 때가 아니라 활성 계정이 바뀔 때다. **토큰 그대로 ≠ 바인딩 그대로.**

동의 현황 화면의 경우, 스키마는 전달되었으나 맥락의 부재로 차이가 생겼습니다.<br>
계약에 동의 테이블의 구조는 있었지만 “앱 계정은 매장과 1:1이고, 따라서 동의는 회원이 아니라 매장 단위”라는 전제가 없었습니다. 담당자는 자기 서비스의 세계관에 맞춰 직원 테이블과 조인했습니다. 각자의 전제 안에서는 합리적이었으나, 틀린 구현이었습니다.

이 사례는 계약에 항목은 있었지만 의미가 비어 있던 경우입니다. 완료 보고와 실제 구현을 대조하면서 발견할 수 있었습니다.<br>
반면 한 기기에 두 계정의 구독이 남았던 문제는 성격이 달랐습니다. 계약에 로그아웃 사건 자체가 없었습니다. 앱과 서버가 계약을 모두 지켰는데도 결과는 틀린 시스템이었습니다. 비교할 문장이 없었기 때문에 로그인하고, 로그아웃하고, 다른 계정으로 다시 로그인해 알림을 보내는 수동 QA에서만 드러났습니다.


| 빈칸             | 결과                 | 발견 방법     |
| -------------- | ------------------ | --------- |
| 항목은 있지만 의미가 없음 | 각자의 전제로 해석한 코드가 존재 | 계약과 구현 대조 |
| 사건 자체가 계약에 없음  | 필요한 코드가 존재하지 않음    | 실제 동작 QA  |


> 대조는 계약을 어긴 구현을 잡고, QA는 계약이 빠뜨린 현실을 잡는다. 둘은 대체재가 아니다.

이후 계약 문서에는 타입과 스키마만 적지 않고, 행위의 의미와 흔한 오해를 문장으로 반복해 넣었습니다.

- 재등록 조건은 토큰 변경이 아니라 활성 계정 변경이다.
- 앱 계정은 매장과 1:1이며 동의는 회원이 아니라 매장 단위다.
- 캠페인 ID는 문자열로 식별자로, 시스템 내부의 자체 숫자 PK와 혼동하면 안 된다.

위임한 작업을 수동 구현으로 가져온 적은 없었습니다.<br>
대신 계약, 구현 대조, 수동 QA라는 검증 루프를 붙였습니다. 위임의 비용은 결국 직접 구현하는 데서 발생한 것이 아니라, **검증할 수 있는 상태를 만드는 데서 발생했습니다.**

이번 작업에서 FCM 연동 자체는 가장 어려운 부분이 아니었습니다.<br>
운영 데이터는 서버가 성공이라고 부르는 사건과 사람이 성공이라고 느끼는 사건이 다르다는 것을 보여줬습니다. 계약 기반 위임은 문서에 적힌 타입보다 적히지 않은 의미가 더 위험하다는 것을 보여줬습니다.

두 이야기는 결국 같은 결론으로 이어집니다.<br>
서버가 관측하지 않는 사건은 성공 지표 뒤에서 사라지고, 계약이 설명하지 않는 의미는 각자의 전제로 채워집니다. 그래서 시스템도 위임도 **보이지 않는 빈칸을 드러내는 장치**가 있어야 했습니다.

> 푸시 서버의 역할은 메시지를 FCM에 넘기는 데서 끝나지 않는다. 누가 받아야 했고, 담당자 앱이 실제로 수신했는지, 수신이 확인되지 않았을 때 무엇을 할지까지 설명할 수 있어야 한다.
